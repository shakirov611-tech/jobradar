# ADR 015 — Общий языковой анализ и персональный Language Fit

Дата: 2026-11-04. Статус: Accepted for implementation; проверка локального развёртывания отдельно.

## Контекст

В baseline анализ языка был частью personal-match, распознавал ru/en/bg и не учитывал уровень кандидата. Collector уже сохраняет общий catalog и отдельные персональные matching-результаты; CRM writer имеет whitelist и автоматическое сопоставление колонок. Нет существующего AI-провайдера или продуктовой БД. Нельзя ограничивать общий сбор языком первого пользователя.

## Решение

Сохранить источники и роли collector. Между нормализацией и персональным matching добавить пользовательски независимый language analysis: только title, description и posting hint. Не передавать профиль, происхождение сотрудников или компанию в AI-классификатор. Требования клиента и команды различать структурно. Language Fit рассчитывать отдельно для каждого search profile; один общий match_score не вводить.

По умолчанию — дешёвые консервативные правила. Для семантического анализа — явно включаемый OpenAI adapter со структурированным ответом, ручной schema/evidence validation, ограничением вызовов/таймаута/повторов. Модель задаётся конфигурацией; CI использует mock. Новых зависимостей нет. Правила не объявлять эквивалентом семантического анализа на всех языках.

Кэш локальных JSON keyed by content + semantic policy: модель, prompt/schema/algorithm version, словари и лимит AI-входа. Профиль не входит в key. Ошибки сохраняются на короткий cooldown; неизвестный результат не равен отрицательному. Ошибка AI не теряет вакансию. JSON manual review привязан к vacancy ID/content hash, хранится отдельно от shared cache и влияет на личный match.

CRM получает два JSON-поля только при явном opt-in, после добавления отсутствующих заголовков. Не изменять старый language, ручные поля, ID или даты. Использовать autoMapInputData с ошибкой для неизвестных колонок и read-back после записи. PostgreSQL не требуется.

Language-aware discovery v1 — отчёт по всем источникам: явные/неизвестные языки, знаменатель ролевых кандидатов и персональная preference yield. Не выключать источники и не менять частоту сбора по малой выборке. Расход обработки пока null, а не выдуманная цена.

## Альтернативы и причины

- Фильтр по языку публикации отвергнут: теряет подходящие команды и смешивает разные признаки.
- AI для всех записей при каждом сборе отвергнут: повторная стоимость без изменения данных.
- Один language score на Vacancy отвергнут: значение зависит от пользователя.
- Автоматическое добавление колонок n8n отвергнуто для первого rollout: ошибочное имя может создать лишнюю колонку; существующая таблица сначала проверяется владельцем.
- Отдельный сервис/БД/векторный индекс отложены: локальные чистые функции и файловый кэш покрывают текущий single-user сценарий.

## Ограничения и пересмотр

Rules v1 понимает ограниченные EN/RU формулировки; новые языковые aliases задаются JSON, другие конструкции требуют AI или ручной проверки. Confidence ordinal, не вероятность. Не выводить CEFR из fluent/proficient. Company/team signals пока только контракт, без автоматического наследования. Старые legacy Airbnb workflow не получают enrichment.

Пересмотреть после размеченной выборки ошибок, замеров API-стоимости/coverage, появления второго пользователя или потребности общего durable cache. До включения платного AI оценить семантический результат на реальных обезличенных вакансиях. До SaaS вынести overrides и UserVacancyMatch в owner-scoped хранилище; существующая географическая политика BG не становится универсальной благодаря этому ADR.
