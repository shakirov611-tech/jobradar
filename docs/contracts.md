# Контракты и границы изменений

Статус: draft для будущей проверки. Не объявлять это контрактом уже проверенного кода.

## Нормализация

Вход: ответ конкретного provider + явный board_token + observation timestamp. Выход: массив отдельных вакансий, каждая с устойчивым vacancy_id. Некорректный envelope завершает run как failed/partial, не как успешный пустой feed. Неполная отдельная запись попадает в quarantine с причиной и run_id, без токенов и полного персонального payload в log.

Проверки: ID/title/source/URL обязательны; timestamps валидны либо null согласно полю; published_at не заполняется временем сбора; first_seen задаёт storage при insert. Remote/geography/language не объединять в один вывод. Description хранить с обозначением формата и безопасно преобразовывать при отображении; не вставлять произвольный HTML в UI.

## Хранилище

Вход: нормализованная вакансия + observed_at + run_id. Insert: сохранить first_seen_at и last_seen_at. Update: whitelist машинных полей и монотонный last_seen_at; first_seen и ручные CRM поля не перезаписывать. Повтор после частичной записи безопасен только при проверенной идентичности ключа и единственном writer в Sheets.

Заголовки Sheets: ровно один vacancy_id и last_seen_at, без пробелов и скрытых копий; автоматическое сопоставление должно быть сверено после refresh schema. Порядок столбцов не использовать как идентификатор поля. Фактическое поведение node проверить экспортом и прогоном на копии CRM.

## Ошибки и повтор

Предлагается: timeout и ограниченные retries с backoff для transient ошибок; 429 учитывать по ответу источника, не повторять бесконечно; auth/schema errors требуют вмешательства. Числа retry и timeout выбрать по измерению, не выдавать за текущие настройки. Run завершён только после фиксации результата storage; количество fetched/normalized/inserted/updated/rejected/errors позволяет найти потерю данных.
