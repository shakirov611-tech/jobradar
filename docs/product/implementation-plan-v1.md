# JobRadar — план реализации v1.0

Дата: 29 октября 2026. Статус: действующий план; текущие статусы ведутся в [roadmap](roadmap.md). Владелец продукта: Денис. Технические решения уточняются по результатам этапов. Численные пороги ниже — предложенные критерии приёмки, а не достигнутые метрики.

## 1. Цель и основной сценарий

Пользователь один раз описывает опыт и условия поиска, получает подходящие вакансии, формирует достоверное резюме под роль, отправляет отклик вручную либо автоматически и видит подтверждённый результат в личной CRM.

Сценарий: профиль → поиск → оценка пригодности → пакет документов → очередь откликов → отправка → подтверждение → CRM → обратная связь.

Генерация резюме и автоотклики входят в основной scope. Первая автоматическая отправка работает по выбранному пользователем списку; самостоятельное добавление вакансий по правилам — следующий уровень автоматизации. Языковая и географическая специфика текущего кандидата — стартовый исследовательский сегмент, не жёсткое ограничение архитектуры на Болгарию или русский язык.

## 2. Актуальная точка

Выпущена v0.6.1. Статусы, доказательства и остаточные ограничения — в [roadmap](roadmap.md).
Сейчас C / MATCH-01; далее D, завершение B и DATA-01 до E. Резюме и реальные отправки ещё не реализованы.
Backup/restore и image digest отложены пользователем до изменения инфраструктуры или второго пользователя.
Критерии A ниже сохраняют целевые требования; отложенные пункты не считаются выполненными и не блокируют C.

## 3. Принципы исполнения

Один законченный пользовательский сценарий на релиз. Сначала техническая проверка самого рискованного канала отправки, затем инвестиции в полный UX. Рабочий сборщик сохраняется. Не писать универсальный робот для всех ATS в первом релизе.

Разделять: подтверждённый факт, вывод модели и неизвестное; техническую ошибку отправки и отказ работодателя; сохранённую вакансию и реальный отклик. Каждый этап заканчивается демонстрацией результата и доказательствами, а не только списком завершённых задач.

## 4. Этапы и критерии перехода

### Этап A. Повторяемая разработка и надёжный сбор

Ценность: изменения проверяются без ручного пересоздания workflow и таблицы.

Работы:
1. Завершить PR #1 при возобновлении; проверить запуск после merge. Обязательность CI для merge — отдельная настройка по согласованной политике.
2. Версия n8n 2.45.5 подтверждена. Digest и проверяемый backup/restore отложены по решению пользователя; вернуться перед изменением инфраструктуры/вторым пользователем.
3. Один раз настроить тестовую Sheets и credential. Написать локальный runner: создать временный workflow/лист, загрузить fixtures, выполнить, прочитать результат, сформировать отчёт, очистить ресурсы.
4. Выбрать API/CLI способ запуска после проверки реальной версии n8n. Если execute API недоступен, runner использует поддерживаемый CLI или закрытый локальный test trigger; универсальный способ заранее не обещаем.
5. Проверить v0.3, затем внедрить с rollback. Добавить first_seen_at при вставке без изменения существующих значений; явные retry/timeout, single writer и run summary отдельными малыми изменениями.

Готово, когда: одна локальная команда проверяет insert/rerun/update/error/manual fields; повтор не даёт новых дублей; first_seen стабилен, last_seen меняется; повреждённый ответ не пишет строки; backup восстановлен на изолированном volume. Файлы/логи остаются пригодными для диагностики даже при падении cleanup.

Минимум ручной работы: один bootstrap тестового окружения и ввод локальных credentials. В дальнейшем fixtures и проверки выполняются автоматически. Runner не открывает n8n в интернет и отказывается работать с ID рабочей CRM.

### Этап B. Проверить канал отправки до масштабной разработки

Ценность: подтверждён хотя бы один реальный путь от документов до отправленного отклика.

Работы: выбрать один ограниченный класс форм; проверить допустимый способ автоматизации, файловые upload, обязательные вопросы, верификацию, распознавание подтверждения и восстановление после сбоя. Начать с контролируемой формы, затем с отдельно разрешённого end-to-end сценария. Публичный Greenhouse GET не даёт доступа к POST без ключа организации; не строить план на таком допущении.

Готово, когда: есть матрица supported/unsupported/required_action, воспроизводимый тест формы, доказательство отправки и тест неоднозначного результата. При timeout после Submit не происходит слепой повтор. CAPTCHA/неподдерживаемая проверка передаётся пользователю, без обхода.

Развилка: если выбранный канал нестабилен или недоступен, выбрать другой канал/адаптер; подготовка резюме и ручной отклик остаются полезным сценарием. Не объявлять автоотклики готовыми по факту одного autofill.

### Этап C. Полезный поиск и объяснимый matching

Ценность: кандидат получает приоритетный список, который действительно стоит проверять.

Работы: отделить источники от профиля; сделать board configuration; определить hard constraints/preferences; разделить remote, eligibility и язык текста/работы/команды; объяснять fit/gaps/unknowns. Добавлять sources постепенно по потребности, а не ради количества. Первый источник остаётся Greenhouse; Airbnb не считать достаточным покрытием целевого рынка.

Сначала детерминированные правила и ручная разметка; LLM только для задач, где простых полей недостаточно. Измерять качество отдельно от количества записей. Не скрывать silently все вакансии с неизвестной зарплатой/языком.

Готово, когда: на фиксированной размеченной выборке нет обхода явно заданных hard exclusions; причины рекомендации проверяемы; false positive/false negative и unknown измеряются; кандидат может сохранить/скрыть/указать причину. Порог полезности определить после первой разметки, не подгонять под текущую выдачу.

### Этап D. Профиль фактов и генерация резюме

Ценность: документ под вакансию готовится быстро и сохраняет достоверность.

Работы: подтверждённая база опыта/навыков/результатов; import CV с проверкой; версия профиля; tailored resume; diff с базой; редактирование; один простой шаблон; PDF с извлекаемым текстом, DOCX при подтверждённой необходимости. Письмо — часть пакета, когда оно нужно для формы или выбрано пользователем.

Готово, когда: можно показать источник каждого существенного утверждения; новые даты, цифры, навыки и роли не добавляются без подтверждения; пакет связан с версией вакансии; отправленный файл неизменяем; тесты extraction/layout и сравнение фактов проходят. Автоматический фактчек не считается абсолютной гарантией — предусмотрена проверка пользователем.

### Этап E. Отклик после проверки пользователем

Ценность: система готовит и заполняет отклик, пользователь контролирует точное содержимое перед отправкой.

Работы: application package и answer bank; state machine; approval привязан к версии пакета; адаптер из этапа B; журнал попыток; duplicate guard; required_action при неизвестном обязательном ответе; ручной fallback.

Готово, когда: end-to-end цепочка работает на поддерживаемом сценарии; статус submitted подтверждается подходящим сигналом работодателя; смена документа отменяет прежнее approval; already applied и unknown блокируют повторную отправку; повторный запуск worker после crash не отправляет второй раз.

### Этап F. Автоотклики с правилами и ограничениями

Ценность: выбранные вакансии обрабатываются без проверки каждой готовой формы.

Работы: explicit opt-in; список вакансий, exclusions, дневной лимит и timezone; утверждённые ответы; пауза; резервирование лимита; предфинальная проверка политики и версии пакета. Затем — автоматическое добавление вакансий по правилам при достаточном качестве matching.

Готово, когда: на тестах проверены два workers, pause/race, дневная граница, отсутствие ответа, изменившаяся форма и crash около Submit; пользователь видит, что отправлено и где требуется действие; неоднозначный результат не расходует новую попытку автоматически. Остановка не обещает отозвать уже ушедший отклик.

### Этап G. Multi-user SaaS pilot

Ценность: другой кандидат проходит путь без Docker, JSON и ручной настройки Sheets.

Работы: auth и ownership; минимальный web UI, onboarding, профиль, выдача, документы, очередь, история/ошибки; hosted постоянно включённый deployment; приватное хранение документов; retention/export/delete; support flow; проверка лицензии n8n и условий источников для фактического UX.

Готово, когда: A не читает/меняет данные B во всех API и документах; пользователь может пройти onboarding и получить результат; восстановление deployment проверено; понятны ограничения поддерживаемых форм; нет скрытого доступа к чужим browser sessions. Пилотная когорта 3–5 человек — предлагаемое ограничение, не существующая база.

## 5. Зависимости и критический путь

A → B (проверка отправки) → E → F. C → E: качество подбора влияет на то, куда подаваться. D → E: отправка использует версионированные документы. После A исследование качества C и технический B могут идти независимо; это не инструкция запускать параллельных агентов.

G требует завершённых single-user сценариев и проверок доступа. Auth из G нужен раньше любого подключения второго пользователя. Проектная DB нужна перед настоящей автоматической отправкой, даже если каталог пока остаётся в Sheets. Не ждать массового SaaS запуска, чтобы защищать state machine.

Ближайшая итерация: C / MATCH-01 — профиль и измерение полезности. Далее D; завершить B и DATA-01 до E. Первый полный пользовательский MVP: C+D+E для одного кандидата и одного канала. F — следующий уровень автоматизации, G — пилот.

## 6. Минимальная целевая архитектура

| Компонент | Роль | Когда вводим |
|---|---|---|
| n8n | Сбор и оркестрация | Сохраняем сейчас |
| JS/модули | Нормализация, правила и проверяемые преобразования | Постепенно из текущего кода |
| Sheets | Текущая CRM и тестовая интеграция | Сохраняем в A–D, дальше projection при необходимости |
| Product PostgreSQL | Версии профиля/пакетов, очередь и состояния откликов, locks/limits | До E/F; tenant boundaries до второго пользователя |
| Renderer + private file storage | Версии резюме и отправленных документов | D/E |
| Один application worker | Поддерживаемый адаптер подачи | B prototype, E production path |
| Один backend + небольшой UI | Auth, права, профиль, действия и результаты | К pilot; точный стек отдельным ADR |

Не использовать внутренние таблицы n8n как продуктовую DB. Первоначально очередь может быть таблицей jobs в product DB: Redis/микросервисы/Kubernetes не обязательны. Масштабировать после измерения lag, latency, ошибок и стоимости. Выбор frameworks и hosting не фиксировать до требований и способа browser execution.

## 7. UX: обязательные экраны первого полного сценария

1. Профиль: факты и условия; неизвестное видно; можно исправить импорт.
2. Вакансии: почему подходит, ограничения и свежесть; save/hide/already applied.
3. Документы: превью резюме, изменения, редактирование и версия.
4. Отправка: режим, пакет, ответы, поддерживаемость и требуемые действия.
5. История: реальный статус, использованные документы, ошибка и следующий шаг.

Один ясный маршрут, без обязательного заполнения всех сведений до первого просмотра вакансий. Дополнительные сведения запрашиваются к нужному действию; без обязательных фактов автоматическую отправку не разрешаем. Состояния «поиск не запускался», «нет подходящих вакансий» и «сбой источника» различаются.

## 9. Тестирование и выпуск

- PR: unit/regression автоматически на GitHub; workflow JS совпадает с source; контракты fixtures.
- Локально одной командой: n8n + тестовая Sheets; fixtures, repeat/update, ошибки и manual fields.
- Для worker: controlled forms, upload, approval, concurrency и crash simulation.
- Периодически: smoke Greenhouse и поддерживаемой формы отдельно от детерминированных tests; без реальной подачи работодателю без разрешённого сценария.
- Для DB/UI: migration/rollback, auth isolation, документные версии и UX tasks.

Каждый PR: проблема, изменение поведения, доказательства проверки, migration/rollback и docs. Связка repository code → exported workflow проверяется автоматически. Полный локальный rebuild и ручная настройка не являются штатным циклом каждого изменения.

## 10. Метрики продукта и эксплуатации

Первичная ценность: время до первой полезной вакансии; доля полезных рекомендаций по оценке кандидата; время от выбора вакансии до готового достоверного пакета; время до подтверждённой отправки.

Надёжность: stale/duplicate rate; invalid records; job lag; supported-form coverage; confirmed submission rate; submission_unknown rate; доля требующих вмешательства попыток; фактологические ошибки резюме; стоимость на пакет/подтверждённый отклик. Знаменатель каждой метрики фиксировать, например submitted / started supported attempts, а не все найденные вакансии.

Результаты кандидата: ответы работодателей/интервью/офферы с задержкой и оговоркой об атрибуции. Количество автооткликов не становится главной целью в ущерб качеству. Платёж/возврат и удержание измерять на платном pilot; поиск работы имеет естественное завершение, поэтому успешный уход пользователя не всегда провал retention.

## 11. Решения, нужные до соответствующего этапа

Сейчас план не блокируют:
- Первоначальный сегмент: проверить гипотезу русскоязычных Product/Growth/Project кандидатов в Европе; не выдавать её за доказанный ICP.
- Режим нагрузки команды: сколько реальных часов в неделю доступно. До этого календарный срок не обещаем.
- Выбор первого канала отклика и целевых форм — решить в B.
- Где будет жить worker и session — решить до E; не открывать текущий localhost ради доступа из облака.
- Модель оплаты, бюджет LLM/hosting, лимит попыток и язык UI — решить на основе pilot scope.
- Политика автоматической генерации: какие факты/ответы утверждаются заранее; что требует человека.

## 12. Оценка и контроль плана

Календарный дедлайн не установлен. Локальный runtime v0.5 проверен пользователем; реальный канал отправки остаётся риском. После оценки C и завершения B уточнить усилия по оставшимся этапам. На каждый эпик давать диапазон усилий и неизвестные, а не единственную дату.

После каждой итерации: что доступно пользователю, какие тесты подтверждают, что осталось неизвестным, какой следующий риск снимается. Обновлять этот план и ADR при смене scope; не добавлять фичи автоматически только потому, что они есть у конкурента.
