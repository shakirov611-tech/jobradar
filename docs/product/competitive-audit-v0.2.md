# JobRadar: конкурентный аудит и требования v0.2

Дата исследования: 29 октября 2026. Статус: предварительное кабинетное исследование пяти продуктов. Метод: официальные страницы и help center; без регистрации, платной подписки, проверки личного кабинета и реальных рекомендаций. Наличие функции означает документированное заявление поставщика, а не подтверждённое качество реализации. Отсутствие подтверждения не означает отсутствия функции. Рекламные показатели экономии времени и роста интервью не использованы как доказанные результаты.

## Цель и выборка

Определить минимальные требования к JobRadar — автоматизированному сбору, персональному подбору и CRM вакансий. Jobright и Simplify — близкие ориентиры персонального подбора; Teal и Huntr — смежные ориентиры CRM; Welcome to the Jungle — ориентир preference-based discovery. Выборка не описывает весь рынок и не доказывает свободную нишу.

## Сравнение

| Продукт | Документированный сценарий | Полезный паттерн для JobRadar | Предел вывода |
|---|---|---|---|
| Jobright | Роль и предпочтения → CV → рекомендации → Match Score и объяснение через Orion | Рекомендация должна помогать принять решение, а не просто сортировать | Качество score и пригодность для BG/RU не проверены |
| Simplify | Профиль → Matches → save/hide/already applied → Tracker; ручное добавление и CSV import | Сбор, решение и CRM соединены; обратная связь; ручной обход автоматизации | Заявленная автоматизация не гарантирует распознавание каждого отклика |
| Teal | Сохранение вакансий через extension/вручную → CRM этапы → notes/contacts/follow-up | Следующий шаг по вакансии и сохранённый контекст важнее длинного каталога | Основной исследованный сценарий — tracker, не доказанный автоматический поиск |
| Huntr | Job clipper → карточка → notes/tasks/documents/interviews | Сохранять описание и историю для возвращения после закрытия страницы | Удобство и полнота импортов не проверены |
| Welcome to the Jungle | Профиль, желаемая роль, контракт, location/remote, опыт → matching | Отделять опыт от желаемой следующей роли и обязательные условия от предпочтений | Документы о скрытии результатов противоречат друг другу; объяснение fit местами обозначено upcoming |

### Отдельные наблюдения

Jobright описывает сопоставление не только по названию, но и по опыту, навыкам и предпочтениям. Это основание включить объяснимость в гипотезы, но не обещать вероятность приглашения на интервью.

Simplify документирует причины match, hide вакансии/компании, already applied, ручной tracker и проверку статуса после отправки. Значимый паттерн: сохранённая карточка и подтверждённый отклик — разные события. Предлагаемые изменения статуса по письмам требуют подтверждения пользователя.

Teal и Huntr демонстрируют, что данные после обнаружения вакансии остаются полезны: описание, дата, заметки и ход отклика. Для JobRadar это поддерживает сохранение личной CRM отдельно от автоматически обновляемого каталога.

Welcome to the Jungle описывает фильтрацию по обязательным условиям, но другая справочная страница утверждает, что вакансии не скрываются. Нельзя восстановить фактическую логику продукта из этих текстов. Для JobRadar требуется прозрачное различие «исключено по условию», «низкий fit» и «неизвестно».

## Позиционирование: проверяемая гипотеза

Кандидату нужен короткий список актуальных вакансий с понятными причинами соответствия, ограничениями по найму и сохранённой историей действий. В качестве начального сегмента можно проверить русскоязычных специалистов, живущих в Европе и ищущих remote работу. Это гипотеза, выросшая из текущего single-user кейса, а не доказанный рыночный спрос. Покрытие этого сегмента конкурентами и готовность платить ещё не установлены.

Нельзя строить отличие только на «AI ищет работу»: несколько исследованных продуктов уже обещают подбор и AI-помощь. Кандидат на отличие — качество проверок географии найма, языковых требований, свежести и объяснения неопределённости. Нельзя утверждать, что конкуренты этого не умеют, без практического теста.

## Требования и приоритеты

M0 — после завершения baseline gate, внутри single-user MVP. P1 — до/в ходе multi-user pilot. Later — только после подтверждения ценности. Ни одно требование ниже не реализовано этим исследованием.

|---|---|---|---|---|

## Изменения архитектуры: только проектирование

- profile: отдельно hard constraints, preferences, experience, target roles; профили версионированы.
- match: reasons, gaps, unknowns, evidence, profile_version, scoring_version; score optional.
- vacancy: published_at, source_updated_at, first_seen_at, last_seen_at, availability и provenance; не смешивать с user status.
- user_vacancy: CRM status, hidden_at, rejection_reason, applied_at, notes; добавлять после проверки существующих полей, без потери данных.
- snapshot описания для контекста отклика: политика хранения и версия; не хранить бесконечно все payload.
- digest delivery: отдельный idempotency key и consent, когда функция попадёт в scope.

Это уточнение предыдущей логической модели, не миграция и не изменение n8n. Baseline gate остаётся первым этапом.

## Как проверить требования, а не скопировать конкурентов

1. Интервью 5 кандидатов из выбранного сегмента: последняя реальная сессия поиска, ограничения, потери времени, способ CRM. Просить примеры, не только пожелания.
2. Ручной benchmark: по 20–30 вакансий на человека; независимая отметка «полезно / не подходит / недостаточно данных» и причина. Эти числа — план исследования, не статистическая гарантия.
3. После разрешения и регистрации: один и тот же тестовый профиль в 2–3 ближайших сервисах; сопоставить пригодность для страны проживания, объяснения и долю устаревших ссылок. Проверить trial/paywall и реальный export/delete, не оценивать по лендингу.
4. Прототип JobRadar: настройка профиля → решение по 5 карточкам → возврат к сохранённой. Наблюдать, понимает ли человек unknown и может ли исправить нерелевантность.
5. Только затем закрепить численные цели и monetization: доля полезных рекомендаций, время до первой полезной вакансии, время на проверку карточки, доля stale/duplicates, повторное использование. Количество собранных вакансий — диагностическая, а не главная метрика.

## Что ещё неизвестно

Реальное качество выдачи пяти сервисов; их покрытие BG/RU/Europe; ограничения trial и текущие цены; полнота источников; проверка актуальности; точность extraction; реакция на изменённый профиль; скрытые paywalls; доступность на мобильном; стоимость эксплуатации и готовность платить. На основании этого аудита нельзя утверждать product-market fit или уникальность JobRadar.

## Обновление scope v0.2: резюме и автоотклики — основные функции

Решение пользователя 29.10.2026 отменяет прежнее предложение отложить эти функции. Gmail sync остаётся отдельной необязательной интеграцией. Новый основной сценарий: профиль фактов → подходящая вакансия → персональный пакет документов → заполнение → отправка → проверка результата → CRM. Baseline gate текущей установки сохраняется; новая функциональность этим документом не реализуется.

### Углублённое сравнение

| Продукт | Подтверждено официальной документацией | Что перенять |
|---|---|---|
| Simplify | Autopilot отправляет без проверки готовой формы; пользователь выбирает поддерживаемую вакансию и настройки заранее. Неизвестный ответ/verification/form могут приводить к failure. Документы сохраняются | Явное различие assisted и automatic; поддерживаемые формы; результат и ручное продолжение |
| Jobright | Пользователь добавляет вакансии в список и запускает Agent; следит за прогрессом и необходимыми действиями. Autofill отдельно оставляет Submit пользователю | Выбранный список как граница разрешённой отправки; required actions; не смешивать autofill и auto-apply |
| Huntr | Base Resume служит основой Tailored Resume; изменения можно проверить. Application Packet связывает резюме, письмо и follow-up с вакансией; PDF/DOCX export | Неизменяемый отправленный пакет, связь с вакансией, база подтверждённых фактов |

Это документированные возможности, без практической проверки. Simplify описывает отправку выбранных пользователем вакансий; это не доказательство полностью автономного выбора любых вакансий. Для JobRadar такой автономный выбор — собственная проектная гипотеза.

### Техническая проверка Greenhouse

Официальный Job Board API допускает публичные GET, но POST application требует Basic Auth с API key организации. Наличие board_token и прочитанной вакансии не является доступом к API отправки. Без партнёрского доступа не проектировать POST как готовый канал автооткликов.

Предлагаемый первый кандидат — адаптер ограниченного набора публичных форм с участием авторизованного пользователем browser worker; способ и допустимость выбираются техническим spike. Не обещать универсальность Greenhouse forms. Не обходить CAPTCHA и access controls: при препятствии — required_action или unsupported. Не получать ключи работодателя путём обхода. Это архитектурные ограничения, а не отказ от автооткликов.

### Требования к резюме и отправке

| ID | Требование | Acceptance criteria |
|---|---|---|
| APP-01 | Подтверждённая база фактов | Опыт, даты, навыки, достижения и ответы имеют версии; импорт из CV требует проверки пользователем |
| APP-02 | Адаптация под вакансию | Видны изменения относительно базы; новая цифра, работодатель или навык без подтверждения блокируют готовность |
| APP-03 | Фактическая опора текста | Каждое существенное утверждение связано с fact ID; semantic review ловит усиление вроде участия → руководства; автоматическая проверка не объявляется гарантией правдивости |
| APP-04 | Пакет отправки | Резюме, письмо, ответы, версия вакансии/профиля и настройки зафиксированы; изменение после отправки создаёт новую версию |
| APP-05 | Документы | Один простой шаблон с извлекаемым текстом; проверить визуально и extraction на поддерживаемом формате; не обещать гарантированный ATS pass |
| APP-06 | Assisted mode | Пользователь проверяет точный пакет и ответы; одобрение связано с их версиями, изменение отменяет одобрение |
| APP-07 | Automatic mode | До включения заданы область вакансий, exclusions, лимит и разрешённые ответы; неизвестный обязательный ответ переводит в required_action |
| APP-08 | Ответы без догадок | Work authorization, sponsorship, зарплата, relocation и иные обязательные декларации используют явные данные пользователя; AI не угадывает |
| APP-09 | Поддерживаемость | До запуска видно supported/unsupported/needs_action; unsupported ведёт на обычную форму с готовым пакетом |
| APP-10 | Журнал результата | submitted требует распознаваемого подтверждения; форма заполнена или HTTP 200 сами по себе недостаточны |
| APP-11 | Защита от повторов | На user+vacancy один активный отклик; submitted и unknown блокируют повтор до сверки; учтён already applied |
| APP-12 | Ошибки отправки | Timeout после финального Submit → unknown, без слепого retry; подтверждённая ошибка до отправки может быть повторена |
| APP-13 | Пауза и лимит | Пауза предотвращает начало новой отправки; проверка перед Submit; уже отправленное не отзывается; лимит резервируется атомарно |
| APP-14 | Наблюдаемость | Пользователь видит прогресс, причину остановки, использованные документы и следующее действие; приватные поля не попадают в общие logs |

Unknown eligibility допустим в рекомендациях, но не является разрешением автоматически заявлять соответствие обязательным условиям. Включение automatic mode должно точно описывать, какие неизвестные условия можно пропустить и какие требуют ответа.

### Модель состояний

draft → preparing → ready → awaiting_approval (assisted) либо queued (automatic policy passed) → filling → submitting → submitted.

Дополнительные состояния: required_action, unsupported, failed_before_submit, submission_unknown, cancelled. Пользовательский CRM этап «отказ работодателя» не равен технической ошибке отправки.

Ключевой переход: таймаут/краш после возможности отправки → submission_unknown. Сначала сверить подтверждение работодателя либо запросить ручную проверку, затем разрешать новый attempt. Внешняя форма не даёт общей гарантии exactly-once.

### Дополнение модели данных

| Сущность | Минимальные поля |
|---|---|
| candidate_facts | fact_id, user_id, type, value, evidence, verified_at, version |
| answer_bank | answer_id, user_id, question_type, value, scope, confirmed_at, version |
| document_versions | document_id, user_id, vacancy_id, fact_version, template_version, content_hash, private_storage_ref, created_at |
| application_packages | package_id, user_id, vacancy_id, document_ids, answers_snapshot, vacancy_snapshot, package_hash |
| application_policies | policy_id, user_id, enabled, scope, exclusions, daily_limit, timezone, allowed_answers, version |

Approval привязан к package_hash; явная правка пакета инвалидирует approval. Приватные файлы не хранятся публичными URL. UNIQUE(user_id, vacancy_id) в applications — один логический отклик; повторные технические попытки внутри него. Cross-source дубли пока не решены автоматически: перед отправкой дополнительная проверка employer/requisition/URL и ручной разбор неоднозначности.

### Архитектура минимальной реализации

Сохранить текущий read pipeline n8n → Sheets. Отдельно добавить, когда baseline подтверждён:
1. Генератор структурированного контента из профиля и вакансии; один renderer документов.
2. Product PostgreSQL для application state, версий, locks и лимитов до автоматической отправки; Sheets остаётся CRM projection. Атомарный контроль отправки не доверять строкам Sheets.
3. Один worker для поддерживаемого способа отправки. Очередь первоначально — таблица заданий в той же БД, без отдельного Redis; lease и recovery проектируются до запуска.
4. n8n оркестрирует, но не является источником истины для application state.
5. Worker в локальном контуре либо будущем hosted deployment; облачная среда не подключается к localhost. Browser profile/session остаётся приватным, не входит в Git/export.

Проверять свежесть вакансии, scope политики, package version и duplicate lock непосредственно перед отправкой. После crash worker не должен автоматически отправлять заново состояние submitting.

### Порядок разработки

| Этап | Результат | Условие готовности |
|---|---|---|
| 0 | Baseline текущего workflow | Экспорт, код, mapping, rerun и restore зафиксированы |
| 1 | Технический spike отправки | На контролируемой тестовой форме проверены upload, questions, confirmation, timeout; выбран один реальный разрешённый способ |
| 2 | Генерация резюме | Подтверждённые факты → документ; diff, редактирование, версионирование, проверки layout/text |
| 3 | Assisted отклик | Один адаптер; точное approval; end-to-end на разрешённой тестовой вакансии; неизвестный результат не повторяется |
| 4 | Automatic mode | Явная policy, atomic limits, stop, unknown handling; контролируемая малая серия выбранных откликов |
| 5 | Pilot и расширение | Измерены фактологические ошибки, supported coverage, confirmed submissions, unknown rate, время вмешательства и стоимость |

Автоотклик по выбранному списку — первый вариант automatic mode. Автономное добавление вакансий по правилам — следующий слой того же целевого сценария после проверки качества matching, а не отмена функции.

### Проверки до реальных отправок

Фактические ошибки в резюме; подмена навыка желаемым; missing authorization answer; повторный enqueue; два workers; лимит на границе дня; pause перед Submit; закрытая вакансия; смена формы; CAPTCHA; crash до/после Submit; false confirmation; повтор после unknown; доступ A к пакету B. Реальные отклики в рамках аудита не отправлялись и автоматически не разрешены фактом утверждения product scope.
