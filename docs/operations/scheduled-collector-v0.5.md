# Локальный сбор по расписанию v0.5

Статус: реализован и покрыт локальными тестами; Windows Task Scheduler и новый
workflow требуют проверки на пользовательском n8n 2.45.5. v0.4 пользователь
подтвердил на рабочей таблице: два запуска без дублей, даты корректны.

## Включение

Обновите файлы проекта, сохранив `.env.integration`. Из PowerShell в корне проекта:

```powershell
npm.cmd run collector:automate
```

Одна команда проверяет конфигурацию, выполняет новый scheduled pipeline с
синтетической вакансией в тестовой таблице и только после успеха регистрирует
задачу Windows `JobRadar Collector`. Первая рабочая сборка — примерно через
минуту; далее каждые 3 часа от момента установки, без зависимости от часового
пояса. Повторная установка заменяет эту задачу и начинает интервал заново.
Настройки нового расписания не требуют ручного импорта, публикации или Execute.

Рабочий лист по умолчанию Vacancies; JR_PRODUCTION_SHEET_NAME меняет его имя.
Тестовый режим пишет только в JR_TEST_SPREADSHEET_ID / JR_TEST_SHEET_NAME,
проверяет отсутствие чужих строк и оставляет синтетическую строку для проверки.
Не очищает тестовую таблицу. Существующий integration runner остаётся доступен.

ПК должен быть включён, пользователь Windows — в системе, Docker и n8n — запущены.
Задача работает без административных прав и пароля, только в текущей пользовательской
сессии. При сне/выключении свежесть не гарантируется; StartWhenAvailable позволяет
запустить пропущенную задачу после возобновления работы, но не воспроизводит каждый
пропущенный интервал. При недоступном n8n следующий интервал пробует заново.
Режим WSL не поддержан установщиком: запускайте npm.cmd из Windows PowerShell.

## Результат и остановка

```powershell
npm.cmd run collector:status
npm.cmd run collector:schedule:status
npm.cmd run collector:schedule:remove
```

Первый показывает latest, lastSuccessfulProduction и lock. Второй — время последнего
и следующего запуска в планировщике, LastTaskResult (0 — успех). Третий удаляет задачу;
он не отменяет уже работающую сборку в n8n. Разовый сбор с той же блокировкой:
`npm.cmd run collector:run`. Тест нового пути: `npm.cmd run collector:test`.

Отчёты лежат в `.collector-state/<runId>.json`, а также latest.json и last-success.json.
В них есть runId, этап, время, outcome, cleanup, counts: total (получено от источника),
matched (прошло текущий фильтр), inserted (новые ID), updated (существовавшие ID,
включая строки без изменения содержимого). Counts отражают подготовленные операции
после подтверждения завершения writer, а не повторное чтение таблицы. Количество
реально изменённых ячеек не измеряется. Поле first_seen по-прежнему ставится только
при вставке. last-success сохраняется после подтверждённого сбора, даже если затем
возникла ошибка cleanup: status в таком отчёте будет failed, причина — cleanup.

При пустом feed или отсутствии подходящих вакансий сбор успешен с нулевыми matched,
inserted и updated. Существующие вакансии не закрываются. Некорректный feed останавливает
выполнение до записи. Полнота корректного, но усечённого upstream feed не определяется.

## Защита и восстановление после ошибки

Runner создаёт running.lock эксклюзивным открытием файла wx. Одновременно может
работать только один runner из этой папки; Windows дополнительно использует IgnoreNew.
Блокировка охватывает и тестовый режим. Не запускайте параллельно v0.4 через Execute,
старый collector, повторную копию папки проекта или прямой webhook: они не используют
этот lock. Это защита одного локального writer, не распределённая блокировка.

Для каждого запуска создаётся временный workflow со случайным 96-битным webhook path,
настроенными Sheets и подтверждением runId в конце. Webhook слушает существующий
loopback n8n; API key не передаётся на webhook и не попадает в отчёт. Секретный path
не печатается. Не публикуйте workflow и не открывайте порт наружу. Случайный path
не заменяет аутентификацию для публичного сервиса.

Читающий Greenhouse GET имеет timeout 30 секунд и до 3 попыток. Workflow timeout —
300 секунд, ожидание webhook — 330 секунд. Повтор записи, POST создания или всего сбора
автоматически не выполняется. Единственный повтор webhook — точное подтверждение
n8n «own webhook not registered»: оно означает, что выполнение не началось.
Успешный workflow деактивируется и удаляется; DELETE 409 ограниченно повторяется.
Его подробные executions могут удаляться вместе с workflow; локальный отчёт остаётся.

При timeout/обрыве после POST webhook, невалидном подтверждении, HTTP-ошибке выполнения
или ошибке cleanup lock остаётся. Следующие запуски возвращают blocked (exit 1).
Workflow деактивируется по возможности, но сохраняется для разбора. Отчёт содержит
inspectUrl. Ошибки без передачи webhook (например, n8n недоступен) не удерживают lock,
если cleanup не требует вмешательства. При неоднозначном ответе POST создания возможен
неактивный workflow-сирота: execution ещё не запускался. Найдите его по runId в имени.

Для восстановления: остановите расписание, откройте inspectUrl, проверьте Executions,
дождитесь завершения или остановите execution в n8n. Проверьте состояние таблицы,
сохраните нужную диагностику и удалите временный workflow этого runId. Только убедившись,
что execution больше не работает, удалите `.collector-state/running.lock`:

```powershell
Remove-Item .collector-state\running.lock
npm.cmd run collector:automate
```

После аварийного завершения Node/Windows lock также может остаться. Его нельзя
удалять автоматически по возрасту: истечение времени не доказывает остановку n8n.
Статус блокировки требует внимания пользователя; push-уведомлений пока нет.
Отчёты не удаляются автоматически; периодически можно удалять старые `<runId>.json`,
сохраняя latest.json, last-success.json и running.lock. Папка исключена из Git.

## Проверено и ограничения

Локально: unit/regression tests, изоляция test/production, исполняемый JS узлов,
пустые feed, блокировка двух runner, retry только при регистрации, неоднозначные
ошибки, cleanup и сохранение last success. Windows Task Scheduler недоступен в
облачной Linux-среде; тестовая сборка и первый scheduled production run проверяются
локально командой включения и последующим collector:status. Это не hosted SaaS и
не гарантия работы при выключенном ПК. Образ Docker, volume и OAuth не меняются.
Backup/restore отложен по решению пользователя; см. ADR 006/007.
