# AI Development Context Engineering v1

## Аудит и решение

Дата: 2026-11-03. Проверенный baseline: [be5dafe](https://github.com/shakirov611-tech/jobradar/commit/be5dafeab2e55994a821a75920086146f71f5170). Аудит выполнен по дереву, исходникам, генераторам, конфигурациям, тестам и документации этой ревизии. Это не проверка установки пользователя.

| Вопрос | Вывод аудита |
|---|---|
| Что реализовано | Node CLI; Greenhouse/Lever; role/remote/personal rules; n8n→Sheets upsert; Windows scheduler; HTML catalog/review; локальные пакеты резюме и drafts; fixture-прототип откликов; Node/browser CI |
| Что уже документировано | Архитектура, data model, ADR 001–014, operations, roadmap/backlog/план, research/evidence, релизы. Создавать их вторые копии не нужно |
| Чего не хватало | Входной инструкции агента, маршрута задача→код→тест, передачи незавершённой работы и измерения стоимости контекста |
| Что дублировалось | Текущие статусы в README, roadmap, backlog и плане; исторические уточнения поверх старых утверждений; два документа CI |
| Что устарело | Отсутствие кода/тестов в tests/README, незакрытый исходный baseline в архитектуре, C как следующий этап после перехода к D, отсутствие drafts после их реализации. Draft contracts обещали quarantine и монотонность timestamp, которых нет |
| Что заставляло читать заново | Восстановление текущей версии из хронологии; поиск CLI и генераторов workflow; выяснение, где правила обзора расходятся с CRM payload; повторный поиск API/retry; выяснение границ fixtures и реального runtime |

Выбран подход: три новых документа (AGENTS, карта кода, этот протокол) и обновление существующих источников. PROJECT_STATUS, ARCHITECTURE и DEVELOPMENT_GUIDE не создаются под новыми именами: их роль уже выполняют roadmap, architecture/current и CONTRIBUTING. Новый ADR не нужен: границы продукта не меняются; это соглашение сопровождения. Архитектурные изменения по-прежнему требуют ADR.

Нет автоматического переписывания документации, новых зависимостей, индекса embeddings или постоянной копии дерева исходников.

## Источники истины

| Вид информации | Основной источник | Когда обновлять |
|---|---|---|
| Поведение и интерфейс | Код + проверяющие тесты | В том же PR, что меняет поведение |
| Команды / версии зависимостей / jobs | package.json, lockfiles, .github/workflows | При изменении конфигурации; руководство лишь объясняет использование |
| Текущий статус и подтверждения | [roadmap](../product/roadmap.md) | При подтверждённом изменении готовности, релизе или новом runtime evidence |
| Следующие задачи | [backlog](../product/backlog.md) | При приоритизации; выполненное переносится в PR/roadmap |
| Scope и критерии этапов | [implementation plan](../product/implementation-plan-v1.md) | При смене scope/критериев, без текущей release-хронологии |
| Компоненты / границы | [architecture/current](../architecture/current.md) | При изменении ответственности или потока |
| Навигация по коду | [codebase-map](../architecture/codebase-map.md) | При новом/перемещённом модуле, интерфейсе, тесте |
| Поля / инварианты | [data-model](../data-model.md) / [contracts](../contracts.md) | При смене схемы/инварианта; target явно отделён от implemented |
| Причины решений | [ADR](../adr/README.md) | Значимый trade-off, альтернатива и условие пересмотра |
| Команды окружения | [CONTRIBUTING](../../CONTRIBUTING.md), специализированный operations по ссылке | При изменении соответствующего сценария |
| API-особенности | [Справочник адаптеров](../research/source-coverage-v0.6.md#справочник-существующих-адаптеров) | При изменении API/адаптера; дата и официальная ссылка |
| Прошлый выпуск / эксперимент | Release notes, Git/PR, research/evidence | Датированный результат; не дописывать туда текущие статусы |

README — вход для пользователя, AGENTS — вход для агента. Они направляют к источникам, не копируют таблицы готовности. Исторические аудиты сохраняются с датой. Если факты расходятся, сначала проверить код/проверки и актуальность evidence, затем исправить основной документ и убрать устаревшую копию.

Внешний технический результат сохраняйте кратко: проверенный endpoint/версия, особенность, тест/место реализации, ссылка, дата, условие повторной проверки. Не сохраняйте полные API-ответы или внешнюю документацию. Локальный справочник не отменяет проверку изменяемой версии API.

## Передача незавершённой задачи

Создавайте **один корневой TASK_HANDOFF.md только при остановке незавершённой работы**, в её рабочей ветке. Не переносите его в main при завершении. Коммит сохраняет handoff и код без персональных данных; при недоступности записи зафиксируйте блокер и не утверждайте, что контекст сохранён. Копию handoff в PR поддерживать не нужно — достаточно ссылки.

Минимальное содержание (обычно до 40 строк; больше только для существенного риска):

```text
Статус: active
Обновлено: YYYY-MM-DD
Ветка: <branch>
Проверенный commit: <SHA до сохранения handoff>
Цель / критерий готовности: <один результат>
Готово: <проверенные шаги>
Решения: <причины или ссылки на ADR>
Изменённые файлы: <пути; где незаконченный код>
Проверки: <команда, результат, commit; что не запускалось>
Проблемы / ограничения: <конкретные блокеры, без секретов>
Следующее действие: <один исполнимый шаг>
```

Возобновление: проверить active, ветку, историю между указанным commit и HEAD и локальный diff. Запись не становится актуальной только из-за наличия файла. При расхождении сверить изменённые области; не повторять весь аудит и не выполнять устаревшее следующее действие вслепую.

Завершение: удалить TASK_HANDOFF.md в той же ветке, результаты/оставшиеся ограничения записать в PR. Если задача отменена, явно закрыть её и удалить файл. История Git сохраняет запись; отдельная папка архивов не нужна. Отсутствие active handoff означает, что продолжение нельзя выводить из старого чата; новую цель задаёт пользователь, приоритеты — roadmap.

## Измерение эффективности

Фактические input/output tokens и стоимость данной сессии не доступны. Экономия токенов **не измерена**. Размер Markdown и сокращение повторов — прокси, а не доказанная стоимость задачи.

Сравнение выполняется на задачах одинакового класса и сложности. Для контролируемого сравнения используйте одну ревизию кода baseline, одинаковые модель/настройки/инструменты и критерии готовности, меняя только комплект контекстной документации. Каждая попытка начинается с пустого контекста в отдельной ветке/копии; порядок старого и нового комплекта чередуется. Не используйте рабочую CRM. Затраты первоначального аудита/подготовки учитываются отдельно от последующих задач.

Начальная выборка: по две сопоставимые задачи в трёх областях — source adapter, HTML review, storage/workflow. Не делайте вывод по одной удачной сессии. Для обычной работы допускается сбор статистики следующих PR без контрольного повтора, но причинность такого сравнения слабее.

| Метрика | Как считать |
|---|---|
| Input / output tokens | Значения из провайдера/trace; отдельно cached input, если доступен. Не переводить символы в токены произвольным коэффициентом |
| Прочитанные файлы | Число уникальных путей; отдельно число операций чтения. Поиск без открытия также считать операцией получения контекста |
| Объём контекста | UTF-8 bytes реально возвращённых фрагментов, результатов поиска, внешних страниц и логов; отдельно уникальные bytes и общий объём |
| Повторные обращения | Повтор того же фрагмента/запроса при неизменном ref; суммарные повторно возвращённые bytes. Отметить оправданные повторы после изменения или для верификации |
| Итерации исправлений | Циклы «неуспешный тест/замечание → правка → перепроверка»; исходную реализацию не считать исправлением |
| Время | Активное время и wall-clock; ожидание CI/пользователя выделять отдельно |
| Тесты | passed / (passed + failed), плюс skipped и перечень suite; число и состав проверок нельзя уменьшать ради процента |
| Регрессии | Подтверждённые дефекты, связанные с изменением, за одинаковое окно после merge (например, 14 дней); до конца окна результат pending |

Достаточно небольшой обезличенной таблицы в описании PR/результатах эксперимента:

```text
task / code SHA / context revision / model / start-end
input_tokens=null; output_tokens=null; cached_input_tokens=null
unique_files; read_calls; context_bytes; repeated_calls; repeated_bytes
fix_iterations; active_minutes; elapsed_minutes; waiting_minutes
checks=[command, SHA, passed, failed, skipped]
review_findings; regressions_14d=pending
trace_available=false; measurement_limits=<что не наблюдалось>
```

Если trace недоступен, оставляйте поля null и измеряйте только доступное (например, размер точного набора прочитанных фрагментов). Не включайте в PR сырой trace с секретами/профилем; используйте агрегаты.

Сравнивайте медианы и разброс по классам задач, сохраняйте неудачные попытки. Успех требует одновременно снижения избыточных чтений/bytes или фактических tokens и сохранения критериев приёмки, полного необходимого набора проверок и качества ревью. Рост регрессий, пропущенные проверки или ухудшение результата отменяют вывод об успехе даже при меньшем контексте. Сначала соберите baseline; затем решайте, нужен ли автоматический сбор метрик. Документы не обновляются инструментом бесконтрольно.
